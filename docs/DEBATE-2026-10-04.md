依据 [OpenAI 官方沙箱文档](https://learn.chatgpt.com/docs/sandboxing)，安装发行版 `bubblewrap`（0.9.0-1ubuntu0.3），从 Ubuntu 的 `apparmor-profiles` 包（4.0.1really4.0.1-0ubuntu0.24.04.8）提取 `usr/share/apparmor/extra-profiles/bwrap-userns-restrict`，安装至 `/etc/apparmor.d/bwrap-userns-restrict`，并使用 `sudo apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict` 加载。不需要系统重启。

只下载并提取该配置，没有安装整个 profiles 包、升级 AppArmor 或关闭全局限制。配置 SHA256：`11d39094f044f0cda0febb3ad517b830301da6b2ce929664af09ee9e4dd264f9`。

`kernel.apparmor_restrict_unprivileged_userns` 保持1。实际 `codex sandbox -c 'sandbox_mode="read-only"' -- ...` 探针确认：技能可读取；外部文件写入被 EROFS 拒绝且原内容未变；TCP socket 被拒绝。

## 工具通道与辩论

沙箱恢复后，发现 Linux 只读沙箱同样拒绝 `socket(AF_UNIX, ...)`，所以直接调用 `fbtool` 不能完成辩论。此限制也有 [OpenAI Codex 上游问题记录](https://github.com/openai/codex/issues/39140)。

为每轮任务注册一个本机 `feishu_bot` MCP stdio 服务，由 Codex 主进程启动 `fbtool --mcp`，再以原来的 Unix socket 和短期令牌路由到 bot。参数遵循 [官方 MCP 配置](https://learn.chatgpt.com/docs/extend/mcp)：限定环境变量、启动时限、工具时限和 required 服务。仅本机这一个由机器人校验能力的服务预授权工具调用，避免非交互 `approval_policy=never` 拒绝调用；没有改动其他 MCP 服务的审批设置。

主任务继续使用原来的 read-only/workspace-write 权限和禁网配置。内部辩手从 bot 执行，无外部工具、无任务令牌、无持久化 bot 会话；每方仅接收自己的历史与对方最终发言。正反双方各五轮，10条发言分别回复当前消息并记录模型、耗时与轮次审计。

工具遵守本轮剩余总时限。主任务结束时先设置取消信号，再回收令牌；辩手取消会杀掉整个子进程组。取消、模型失败、发送失败都停止后续轮次。本轮禁止重复启动整场，防止重复发送。

以 `辩论话题：...`、`辩题：...` 或 `$feishu-debate ...` 开头的明确任务必须有成功的真实工具执行，否则最终回执改为“独立辩论未完成”，报告已推送数量。任何自然语言任务中，已尝试但失败的辩论工具也触发该检查。主模型自身的额度/认证错误保留，不改写为未调用工具。技能明确禁止使用单模型模拟补齐，查询或检查辩论模式不会启动辩论。
