## 仍值得做的优化

1. **Codex JSONL 流式解析和输出上限**（`codex_runner.run_codex`）：目前 `communicate()` 保留完整 stdout/stderr，之后又建立事件列表。长任务或大规模命令输出增加内存占用。建议用临时文件或增量解析保留最终答案、动作摘要和有限错误尾部。
2. **会话路径及 context 元信息缓存**（`codex_runner._session_path/session_context`）：目前多次遍历全部会话目录和重读日志；按 SID 缓存路径、按文件 mtime/size 缓存元信息，删除及新写入时失效。路径不存在的结果不应永久缓存。
3. **任务队列上限与等待提示**（`Bot.inbox/task_queue`）：两个队列目前没有容量限制；持续消息输入可以积压。需要确定群内容量和拒绝/重试文案，再加入有界队列或持久化任务调度。
4. **合并审计事务与失败重试**（`Bot.audit/db`）：一轮 user/assistant 仍分别提交，普通审计写入仍采用尽力记录。合并为一次事务、增加短暂失败重试和审计欠账队列，可减少 DB 往返和半轮记录。
5. **共享知识库内存与避免无变化重建**：空间级锁已防止错误，但多个 Bot 仍分别持有矩阵；定时同步无变更时仍读写索引/全文副本。可以引入空间级索引缓存及版本检测。此次不改变同步策略。
6. **大附件下载的内存占用**：当前 SDK 先获取完整内容，再判断 50 MB 限额；并行下载会产生峰值内存。需要评估 SDK 的流式接口或隔离下载服务。

长回复重试现在避免重发已明确成功的段落；网络中断时服务端已接收、客户端尚未收到回执的情形仍有重发歧义，需要接口幂等标识才能进一步保证。以上属于后续优化边界。
